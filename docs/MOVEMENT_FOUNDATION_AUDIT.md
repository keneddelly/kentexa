# Movement foundation audit — candidate after the Stage 3K–3R custody gate

Date: 2026-09-27. Read-only repository and production database review. This is an architecture gate, not a migration or a Kentexa Van launch. The current production branch is `76d01ad6e13d5ba386eda511a0a70edf66cc5b04`; Stage 3K–3R behavior remains in draft PR #47, with retry integration in draft PR #49.

## Existing authority

| Concept | Current code | Meaning and limit |
| --- | --- | --- |
| Shipment | `shipments/entities/shipment.entity.ts` | Transport demand and the structured location/hub decision. A walk-in counter Order + Parcel can currently have no Shipment; do not invent one for historical rows. |
| Parcel + custody | `super-agents/entities/parcel.entity.ts`, `parcel-custody-event.entity.ts` | Physical object and append-only custody history. Stage 3K–3R is closing last-mile proof and cash liability. |
| BulkShipment | `super-agents/entities/bulk-shipment.entity.ts` | Active origin-hub grouping of several Parcels with a destination and aggregate cost; `parcel.bulkShipmentId` is its membership. Its dispatch is not proof that a carrier physically accepted custody. |
| TransportAssignment | `transport/entities/transport-assignment.entity.ts` | Responsibility of a provider for one Parcel, with an availability slot and proof fields. It can point to the Parcel and its Shipment; no shared run identity exists. |
| ProviderAvailability | `transport/entities/provider-availability.entity.ts` | Published provider capacity/time slot. It is not a particular vehicle or an immutable executed trip. |
| DailyBatch / BatchParcel | `daily-batches/` | Older Kariakoo-specific Van/zone model linked to Order. `DailyBatchesModule` is not imported by `AppModule`, so its routes are dormant. Its delivered status and notifications would be a separate delivery authority if reactivated unchanged. |

Read-only production counts: 83 Parcels, 2 BulkShipments (one open, one dispatched), 2 Parcels in a bulk group, 1 TransportAssignment with a Parcel reference, 0 assignments with a Shipment reference, 0 DailyBatches and 0 BatchParcels. These are counts at audit time, not migration targets.

Read-only inspection of the two historical groups: BulkShipment #1 (Dar es Salaam → Arusha City) has one dispatched Parcel #18, a transport company/reference and a dispatch timestamp; #2 (Dar es Salaam → Mwanza) has one received-at-hub Parcel #21 and remains open. Neither Parcel has a TransportAssignment or custody event in the current ledger. These pre-ledger records do not establish who physically held them. They must not be inferred as completed Runs or backfilled with carrier custody.

## Decision for the next gate

Use the existing Parcel, custody event and TransportAssignment authorities. Do not activate DailyBatchesModule or use BatchParcel's `DELIVERED` state as a second proof of delivery. Preserve existing BulkShipment records and operational behavior; do not rename or backfill them merely to introduce a Run.

A future **Movement/Run** is one physical departure with a responsible transport operator, time, capacity and origin/destination logistics points. Many Parcel-specific assignments may refer to one Run. A **van is a transport mode/vehicle type**, not a Kentexa-only operator or a separate logistics domain. A Van Run may be supplied by Kentexa-controlled capacity or by a verified partner transport provider; buses, trucks and motorcycles use the same Run/assignment principles where appropriate. Vehicle ownership, run operator, customer-facing service name and physical custodian are distinct facts. A Run does not create a second Shipment, Parcel or delivery status. Actual handover still requires the Parcel custody writer and its authorized receiving actor.

The first implementation slice should be deliberately small: one scheduled departure, one verified operator, vehicle type/reference where known, a configured corridor with ordered operational stops, and membership of multiple existing Parcels through their assignment. Each Parcel has a validated boarding and unloading point on that Run; capacity is occupied only for the segments it rides. No payroll, fleet maintenance, route optimization, automatic dispatch or multi-stop solver. Keep place identifiers/snapshots and capacity validation under their existing authoritative domains. Kentexa may coordinate or brand a service without owning the van or employing its operator; record contractual operator and asset ownership explicitly where known, never infer either from a logo or free text.

`BulkShipment` is an origin-hub packing/grouping object in the current code. Its open state accepts compatible Parcels; dispatch marks the group and Parcels dispatched, but stores no shared verified carrier acceptance, vehicle, capacity reservation or per-Parcel custody transfer. Do not promote its status into a Run state. A Run may carry Parcels from one or more compatible groups, while the existing bulk grouping remains a separate operational object.

The single-Parcel path can bind an accepted TransportAssignment at dispatch. The provider's authenticated `COLLECTED` action then writes `transport_provider_collected` custody evidence under Parcel and assignment locks. The destination hub receipt validates that evidence when it exists; legacy parcels without it retain unknown previous custodian. The bulk dispatch path instead updates statuses and tracking in a transaction but does not bind an assignment or write carrier custody. The pilot must make each Van Parcel's authorized operator confirm collection explicitly, whether that operator is a verified partner or Kentexa-controlled; a bulk dispatch label cannot stand in for that handoff. The existing provider-role writer must be extended or an equivalently guarded Kentexa-operator writer added before claiming Kentexa-controlled collection works.

`createAssignment()` currently reserves an availability slot separately from saving an assignment and resolves the acting Super Agent from the caller's user ID. Before a Van Run accepts live parcels, move capacity/membership and active hub-role validation into one transaction with row locks, an idempotency key and a unique active assignment rule. Define cancellation release and concurrent additions. A planned seat or kilogram count never implies possession.

## Milk-run pilot: request, pickup or desk intake

This is a **milk-run service**: scheduled vans repeatedly collect and drop off many customers' Parcels along configured local corridors, rather than treating one customer order as one vehicle trip. Initial Dar es Salaam operating areas are **Kariakoo, Mbagala, Ubungo, Mbezi and Bunju**. These are pilot areas, not a permanent fixed route or hardcoded city list. Operations must define actual stop order, times, receiving hubs/handoff points, fares and service availability for each corridor before sale. Some departures may connect only two points; others may serve several stops. An area name alone does not prove a hub exists there or that a Van will run today.

The service has **two independent intake doors**. Any authenticated person, including a seller acting for an authorized business or an ordinary user sending personal goods, can create a standalone Shipment and request Agent pickup. A person without a Kentexa account can bring goods to a Super Agent desk for assisted registration; the hub records that person's sender identity and contact. Both doors use the same Parcel, tracking and custody authority and can join a compatible Van Run where the selected service uses one. A marketplace sale may also create transport demand, but a sale or seller role is never a prerequisite for sending a Parcel. The requester, physical sender, business, payer, recipient and eventual Parcel custodian may be different parties; record their actual roles without rewriting everyone as a buyer or seller.

**One logistics capability serves every sender.** Service eligibility, quotes, pickup tasks, Parcel identity, tracking, handoffs, delivery proof and dispute evidence follow the requested route and service, not the sender's commerce role. Authorization still follows the entry door: an account holder acts for their own request, a seller's business context authorizes business-linked goods, and a Super Agent's active hub context authorizes assisted desk intake. A desk-created counter Order may supply a receipt, but it does not turn a walk-in into a marketplace buyer or require an account. The platform must not fork Parcel and custody rules into separate seller, buyer and guest logistics engines.

**Hub mediation is optional for Kentexa logistics.** For an intracity direct delivery, the same authorized Agent may collect from the sender and deliver to the recipient: sender → Agent → recipient, with verified collection and delivery evidence on the same Parcel. No Super Agent, BulkShipment or Movement/Run is required. If another Agent takes over, record an explicit Agent-to-Agent custody handoff; an assignment change alone does not transfer possession. A hub is required only for a service path that actually includes desk intake, hub handling or a hub-based transport connection. The pilot's Van path may use hubs, but it must not turn every Parcel into a hub Parcel. The selected service path and physical custody events determine the next action; proximity to a hub does not.

The desk path must work **without a marketplace order or a seller account**. The hub operator records sender, recipient, goods, declared value, destination, agreed charge and collection; the existing `POST /super-agents/offline-intercity` path already creates a counter Order, Parcel, tracking number, receipt and origin-hub custody event for this case. That Order is a receipt/tracking record, not a marketplace purchase. Keep the hub's active role and cash authority intact.

The remote-request path starts at the existing `POST /shipments` and confirmation flow: an authenticated user can request transport independently of Commerce; confirmation creates one pending Parcel with durable hub decisions, including `not_required` when hub mediation was not requested. Its `pickupOption` (`door`/`agent`/`station`) is currently a stored preference, **not an Agent assignment, Super Agent selection or physical pickup**. The pilot still needs a guarded Agent pickup request/acceptance, first-mile assignment, sender-to-Agent custody evidence and safe retry/decline handling. A hub-mediated path additionally needs Agent-to-hub handoff and hub receipt. A direct intracity path needs verified recipient delivery instead. Do not mark a pending Parcel received at a hub because a hub id was selected. A quoted, eligible Run may hold capacity before pickup with an explicit expiry/cancellation rule; a bare pickup request is not a booking. Boarding/dispatch requires the Parcel to be physically present at the correct point and the operator to confirm collection.

### Connect the existing roles through one parcel journey

| Actor | Creates or confirms | Authority boundary |
| --- | --- | --- |
| Ordinary account holder | Independent Shipment for personal or other authorized goods, with pickup and destination choices | Owns the request; is not automatically the physical sender, recipient, seller or carrier. |
| Seller/business | Shipment for sold goods, linked to its actual Sale/Order when applicable | Active business context authorizes its sale and shipment; it does not grant Agent or hub powers. |
| Walk-in sender | Presents goods and contact details at an authorized Super Agent desk without a marketplace purchase or account | The hub records the actual sender and recipient; its active context authorizes assisted intake, not a fabricated sender account. |
| Pickup Agent | Accepts a specific pickup task, records sender handoff, then delivers directly or takes the Parcel to the selected origin hub | Physical possession begins only at verified collection; an availability toggle is not custody. |
| Origin Super Agent | Registers walk-ins or confirms receipt from Agent/sender, groups physically held Parcels and prepares them for a Run | Its active hub context controls hub writes; a planned hub decision alone is not receipt. |
| Van operator/transport provider | Publishes/accepts a compatible Run and confirms each Parcel collected, departed and transferred | Assignment/Run is movement responsibility; authenticated collection and receiving events prove custody. |
| Destination Super Agent/Agent | Receives a hub-routed Parcel or performs authorized delivery | A hub receipt applies only to a hub-routed Parcel; recipient delivery always needs its own proof. |

Use the existing Shipment → Parcel path for an independent request and the existing Order → Parcel path for a seller sale or desk receipt. They converge at **one Parcel identity and one custody ledger**. Only Parcels actually using a scheduled transport service consume Run capacity; direct Agent delivery does not. The existing KTX-SHP and Parcel/Order tracking identifiers can both resolve to that journey without duplicating physical events. Link communications and notifications to those canonical IDs and the active actor context; do not copy the same parcel into disconnected Agent, hub, transport or seller dashboards. A handoff should expose the next actor's actionable task and confirmation, with retries that do not mint duplicate Parcels, assignments or custody events.

Current gaps are concrete: seller `needsCollection` is accepted on the seller shipment DTO but does not create an origin pickup assignment; independent Shipment `pickupOption` is only persisted; `createAssignment()` targets a transport provider, not a first-mile Agent; bulk dispatch updates Parcel status without carrier custody. Existing destination Agent claiming/delivery is a separate last-mile path and must not be mistaken for origin collection. The next integration slice should make the first-mile Agent task and its guarded terminal action work for a confirmed independent Shipment: verified direct recipient delivery or selected hub receipt, according to the requested service. Reuse that path for seller parcels under their business scope. The Run slice follows once hub-routed intake is physically proven.

### First-mile implementation gate

1. A requester or authorized seller asks for **origin pickup** against an existing confirmed Shipment/Parcel or seller Parcel. Persist the origin address/place snapshot, pickup contact, quoted pickup fee, requested service path and request state. Store a target origin hub only when hub mediation was explicitly selected and validated. Keep Shipment/Order ownership and active business context as the write authority. Do not derive a physical pickup task or a Super Agent decision from the legacy word `agent` alone; it establishes neither.
2. Make one pickup task per active Parcel pickup request. An approved Agent in the service area, acting in the active Agent context, claims it by an atomic compare-and-set. The task records its own Agent identity, accepted time and state; destination delivery claims remain separate. Decline, cancellation and expiry release the claim without erasing audit history.
3. Agent collection locks the Parcel and task, verifies the assigned Agent, requires sender handoff evidence, inserts an idempotent `origin_agent_collected` custody event, and advances Parcel tracking in the same transaction. A mere claim, location ping or uploaded photo must not advance custody independently.
4. For a hub-mediated path, the selected origin Super Agent confirms the Agent-to-hub handoff against that last custody event. Under Parcel/task locks, insert an idempotent `origin_hub_received` event from that exact Agent to the active hub, update Parcel status and tracking together. A hub cannot receive a different Agent's task, and an Agent cannot mark the hub as received. For direct intracity delivery, the assigned Agent completes verified recipient handoff on the same Parcel without manufacturing a hub receipt. An Agent-to-Agent transfer requires its own verified custody event before the receiving Agent may deliver.
5. Reconcile the pickup charge and Agent earning only once after the defined billable event; keep the Van fare, hub fee and COD goods liability separate. Prove cancellation before/after collection, duplicate requests, two Agents racing to claim, stale active roles, offline retry, hub refusal on a hub path, direct recipient proof, and no possible Van boarding before the required physical handoff.

### Direct intracity delivery boundary

The current production-branch `ParcelCollectionsService` already has an Order-linked collection job, atomic Agent claim and `seller_collected_by_agent` Parcel custody write, but its normal terminal path is receiving-hub confirmation. It does not create a pickup task for an independent Shipment, and its collection evidence does not by itself establish recipient delivery. `AgentOrdersService` has Order-level claim, pickup and delivery actions, but those status updates are not the canonical Parcel custody proof for a standalone Shipment. Reuse the relevant Agent and Parcel authority only after checking the Stage 3K–3R candidate; do not route direct deliveries through a fake hub or mark an Order delivered as a substitute for recipient proof.

For a direct service, the Agent who holds the Parcel after verified sender collection may deliver it to the intended recipient. Under a single locked Parcel/task boundary, validate the active Agent role, current custodian, recipient evidence, terminal status and idempotency key; append the recipient handoff event and update tracking together. A retry returns the same result, and an unverified Agent or a second claimant cannot complete delivery. A transfer to a different Agent first requires an explicit, accepted custody event. The hub decision remains `not_required` on sides where no hub was requested. Any Order or Shipment status projection follows the proven Parcel event and must preserve separate COD and payment rules.

After receipt at a participating origin hub, a hub-routed Parcel can be offered a compatible scheduled Van Run, operated by Kentexa or a verified partner under the same transport rules. Confirmed Run membership records planned capacity, while the existing custody handoff records physical transfer to the authorized operator. At the destination, a receiving hub confirms custody before pickup or last-mile delivery when that Run uses a destination hub. Direct intracity Parcels bypass this Run path and proceed to verified recipient delivery. The public can track verified parcel events. Marketplace-origin Parcels may later join the same Run; neither source gets a parallel Van shipment or tracking system.

For an initial local-market pilot, define a real origin hub, destination hub/handoff, boarding/unloading stops, departure window, available capacity on every occupied segment, verified operator and fare before the desk quotes a Van option. Show the actual operator where it matters to the customer; a partner van must not be represented as Kentexa-owned. If no eligible Run exists, the desk must not promise Van delivery. Counter intake can continue using other available transport. Do not equate `offline_intercity`'s current `shippingMethod: 'agent'` with proof of Van assignment; a separate validated Run choice and subsequent custody handoff are required. The Van pilot therefore depends on the counter/custody and movement gates, **not on completion of marketplace checkout**.

## Required review before coding

1. Close the Stage 3K–3R phone, recipient proof and Agent COD/remittance gate. The currently isolated staging test must not be redirected to this candidate.
2. Decide whether a BulkShipment maps to a packing/grouping object, a Run, or both in each current operational path. Inspect the two historical production rows read-only; do not reclassify them from status alone.
3. Trace single-Parcel and bulk dispatch, provider acceptance, origin-hub handoff and destination receipt to their canonical custody events. Assignment and planned Run membership must never alone imply physical custody.
4. Define one transaction for adding/removing compatible Parcel assignments under per-segment capacity and role/business authority; prove two concurrent additions cannot overbook or double-assign. Reuse existing availability validation where it truly applies.
5. Design an additive nullable Run reference and migration for new assignments only. Preserve historical nullable assignment references; no inferred backfill. Prove rollback, retry and public tracking projection on PostgreSQL before any production migration.
6. Prove both pilot doors without marketplace checkout: unregistered walk-in desk registration with receipt/tracking, and an independent account holder or authorized seller Shipment request followed by Agent pickup and, for a hub-routed service, hub handoff. Also prove direct intracity Agent delivery without a hub or Run. Then assign a physically received hub-routed Parcel to an available Run and prove carrier collection, full/unavailable Run behavior, retry and destination receipt. Preserve distinct requester, physical sender, payer and recipient identities.

The human flow remains “Tuma Mzigo” and “Fuatilia.” Movement grouping and provider details are operational infrastructure, while public tracking reports only verified parcel events and the next meaningful step.
