## 2. What already exists and should be reused — by far the largest finding

Stage 3S-B is not starting from nothing. Several pieces Issue #61 asks for are **already built**, just not fully connected to each other:

| Capacity/assignment integrity underneath a booking | `slot-capacity.ts`'s atomic reserve/release primitives, `createAssignment`'s now-transactional reservation (Stage 3S-B1) | `src/transport/slot-capacity.ts`, `transport.service.ts` |

**Conclusion: reuse, don't rebuild.** `TransportRoute` is the Transporter+Route authority; `ProviderAvailability` is the schedule/capacity authority; `Shipment` is the demand+accepted-selection authority; `TransportAssignment`+custody is the fulfillment authority. Stage 3S-B's job is to **connect and extend** these, not invent parallel ones.

## 3. Missing pieces

1. **No comparison/sorting.** `findAvailableForRoute` sorts by `date ASC, departureTime ASC` only — hard-coded "earliest departure." No "cheapest" or "fastest" option, and no client-facing sort parameter at all. `estimatedHours` (the one journey-duration field that exists, on `TransportRoute`) isn't even joined into the public discovery result today.
2. **No itemized quote.** `priceQuoted` is one flat number. Issue #61 requires `transport base + first-mile Agent pickup + hub/Super Agent handling + last-mile delivery + Kentexa platform charge = final price`, and a persisted quote (transporter/service, route, schedule, price components, quote timestamp/version) that later route-price edits cannot mutate. Today, updating `TransportRoute.pricePerKg`/`.fixedFee` is a plain in-place update with **no history at all** — a Shipment created yesterday at the old price has no independent record if anyone ever needed to audit it (its own `priceQuoted` value is the only surviving evidence, not a first-class quote row).
3. **A real duplicate pricing system already exists — this is the concrete case Issue #61's "no duplicate" rule is protecting against.** The Super Agent counter/dispatch flow (`createOfflineIntercityOrder`, walk-in "Nataka kutuma mzigo Mwanza") prices shipments through **`ShippingRate`** — a completely separate table (per-hub, per-city-pair flat rate + minimum charge, `src/super-agents/entities/shipping-rate.entity.ts`), read via `getShippingRates()`/the inline weight×rate-vs-minimum calculation in `super-agents.service.ts` (~lines 370-492). It has **no relationship to `TransportProvider`, `TransportRoute`, or `estimateShipmentPrice()` at all.** Issue #61 explicitly requires the Super Agent counter to "use the SAME canonical discovery/quote service" — today it uses a different one. Unifying this (without breaking existing Super Agent hub pricing) is the single largest de-duplication task in this stage.
4. **No Movement/Run closure yet** (separately tracked, `docs/stage3s-movement-readiness-audit.md`, this same repository): `ProviderAvailability.status` is never actually set to `DEPARTED` anywhere in the code today. Not this issue's scope, but discovery/quote results will surface `ProviderAvailability` rows whose lifecycle is still incomplete — worth knowing, not blocking.
5. **Kentexa Van (`daily-batches/`) is fully outside this whole system**, confirmed again here: zero references to `TransportProvider`/`ProviderAvailability`/`TransportRoute` anywhere in `daily-batches.service.ts`. It has its own `DailyBatch`+`BatchParcel` domain, its own status enum, and (implicitly, from its Kariakoo-hub design) its own undiscovered pricing — it will never appear in a `findAvailableForRoute` search result as it stands. Issue #61 explicitly forbids "reactivating DailyBatches as a shortcut" — correctly anticipating that the tempting move here (route van pricing through the discovery service by quickly wiring DailyBatch in) is out of scope; Van should instead become a normal `TransportProvider` with `RouteType.LOCAL_LOOP` routes over time, which the schema already anticipates (see the movement-readiness audit, §1).
6. **No Intent-facing contract yet.** `findPublicProvidersForRoute` was clearly built with an AI/Intent caller in mind (its own doc comment says so) but nothing in `src/ai/` or `src/search/` currently calls it — confirmed by a direct search for its call sites (only the public HTTP route calls it). Intent compatibility is anticipated in shape, not yet wired.
7. **No price-basis flexibility.** Only per-kg + flat-minimum exists on `TransportRoute`. Issue #61 asks for parcel-count/weight/size/service-class as pricing bases — none but weight exists today.
8. **No effective-dates window** on route pricing (only a plain `isActive` boolean) — "retain price history, never silently overwrite historical accepted pricing" needs a real history mechanism, not just the accepted Shipment's own frozen `priceQuoted`.

## 4. Exact entities/tables/services/endpoints/UI to extend (not create fresh, except where noted)

- **Extend, don't replace:** `TransportRoute` (add price-basis type, effective-dates, service-class fields), `ProviderAvailability` (already sufficient as the schedule/capacity ledger — likely no change needed), `Shipment` (already has the accepted-selection FKs; add itemized price component fields or a linked quote row).
- **New, additive:** a `RoutePriceHistory`-style table (or an append-only price-version table keyed to `TransportRoute`) so a price edit never mutates history — satisfies "retain price history" and "accepted quote economics immutable" without touching `TransportRoute`'s current row shape.
- **New, additive:** a `Quote` (or `ShipmentQuote`) entity/table capturing the itemized breakdown + snapshot timestamp/version, created at "customer chose an option" time and referenced (not copied) by the Shipment once created — this is the concrete mechanism for "selection/quote != custody" and "transport assignment/booking != custody" (Issue #61's own hard rules): a Quote is neither a booking nor a custody event, just a frozen commercial fact.
- **Extend `TransportService.findAvailableForRoute`**: add a `sortBy` parameter (cheapest/fastest/earliest), join `estimatedHours` into the result, and return the itemized quote shape instead of (or alongside) the current flat `pricePerKg`/`fixedFee`.
- **New endpoint(s)**: a "get a quote" call that takes the customer's chosen `availabilityId` (+ pickup/delivery handoff options + weight) and returns the itemized final price *before* `createShipment()` is called — `createShipment`/`confirmShipment` then reference that quote rather than recomputing price inline as `estimateShipmentPrice()` does today.
- **Reconcile, carefully:** `super-agents.service.ts`'s `createOfflineIntercityOrder`/`getShippingRates`/inline fee calculation — the walk-in counter path needs to call the *same* quote service `Shipment` uses. This is the riskiest single change in the stage: `ShippingRate` is live, in active use, and has real historical Super Agent pricing behavior depended on by existing hubs. Do not delete or silently reinterpret it; migrate call sites onto the canonical service behind a compatible contract, with `ShippingRate` becoming (at most) a per-hub *fallback/legacy* rate source feeding into the same quote output shape, not a second independent pricing engine.
- **UI**: a public "search transport" page/flow calling the extended discovery endpoint (new UI, since none exists today beyond the coverage map), a quote-review step before Shipment creation, and a Super Agent counter screen update to call the same service instead of its own rate lookup.

## 5. Migration plan and risks

- **Next timestamp: `1788283800000`** (see §1). Any new table (price history, quote) is purely additive — new tables, nullable/new FKs on existing rows — so it can ship with `IF NOT EXISTS`-guarded, reversible migrations following the exact hygiene pattern already established for this lineage (see the walk-in-idempotency migration's C2 correction on the Issue #60 side: `CREATE TABLE IF NOT EXISTS`, a `DOWN` that refuses when historical rows exist).
- **Risk: `TransportRoute` schema changes.** Adding price-basis/effective-dates columns to a table with **live rows and a live pricing computation (`estimateShipmentPrice`)** must be additive/nullable-with-safe-defaults only — never change the meaning of `pricePerKg`/`fixedFee` in place, since `estimateShipmentPrice()` and any in-flight Shipment reference them by current value today.
- **Risk: ordering/uniqueness guard.** This lineage already has a `migration-timestamps.spec.ts` guard proving no duplicate migration timestamp exists; any new migration must keep passing it, plus a clean-schema UP→DOWN→re-UP native-PostgreSQL proof, matching every prior stage in this chain.
- **No risk to production**: nothing in #47→#49→3S-A→3S-B1→(this stage) is deployed to production. A Stage 3S-B migration lands on the SAME as-yet-unreleased branch chain; production's own next real migration is still whatever Issue #60's rehearsal eventually authorizes (`1788282000000`+ for the walk-in work), entirely independent of this.

## 6. Stage 3S-A / prerequisite custody-lineage dependency

**No blocking dependency found.** Stage 3S-B is a *demand-and-pricing-side* extension (discovery, quote, Shipment creation) that sits **before** first-mile custody begins — it reads `TransportRoute`/`ProviderAvailability` (read-only for discovery) and writes `Shipment` rows exactly as `createShipment()` already does today. It does not touch `parcel_custody_event`, `assertFirstMileComplete`, or any of 3S-A's collection-handoff guards, and does not need Stage 3S-B1's assignment-integrity fixes to be *merged* anywhere first (3S-B1 hardens `TransportAssignment`/capacity reservation, which Stage 3S-B's quote/discovery layer sits upstream of, not on top of). The one real interaction point — `reserveSlot()`/capacity reservation at Shipment creation — is already the hardened, transaction-safe path from Stage 2C/3S-B1; Stage 3S-B should call it exactly as `createShipment()` already does, not reimplement it.

The one thing worth flagging, not blocking: **none of #47→3S-B1 is in production or even in staging beyond the isolated Stage3KR rehearsal environment**, and that rehearsal (Issue #60) is a *different* feature slice (recipient journey, custody, COD) mid-flight on the same underlying schema lineage. Stage 3S-B's own future staging/rehearsal, when it comes, should be sequenced *after* Issue #60's gate closes or on a fully separate isolated environment, to avoid two live rehearsals mutating the same disposable database at once — an operational sequencing note, not an architectural blocker.

## 7. Recommended first bounded implementation gate

Smallest safe slice, in order:

1. **Extend `findAvailableForRoute`/`findPublicAvailabilityForRoute` with `sortBy` (cheapest/fastest/earliest) and join `estimatedHours`.** Pure read-side, no schema change, no new entity, immediately testable, and it alone satisfies "search → compare" for the existing (already-public) discovery endpoint. Zero risk to any write path.
2. **Introduce the `Quote` concept as a pure computation + optional persisted row**, additive migration, derived from the exact same inputs `estimateShipmentPrice()` already uses (route + weight) plus the new itemized components (first-mile/hub/last-mile/platform fee — each either `0` or looked up from whatever authority already prices that leg, e.g. the Agent's existing `deliveryCommission` for last-mile). `createShipment()`/`confirmShipment()` start referencing a Quote's snapshot instead of recomputing inline, with the exact same net price for a pure per-kg route as before it existed (a strict behavior-preserving refactor first, itemization second).
3. **Only after (1) and (2) are proven** (regression against the existing `shipment-capacity.real-postgres.spec.ts` suite, which already exercises `createShipment`/`confirmShipment` heavily — it must stay green throughout): reconcile the Super Agent counter's `ShippingRate` path onto the same Quote service, as its own, separately-reviewed slice — this is the highest-risk change (live hub pricing behavior) and should not be bundled with (1)/(2).
4. Route pricing history/versioning and the public-facing "search transport" UI, Intent wiring, and Kentexa Van's eventual migration into `TransportProvider` all follow as later, independently-gated slices — not part of the first bounded gate.

Nothing above touches production, Stage3KR staging, or `daily-batches`. No implementation has been started.
