# Stage 3R — local Agent COD cash remittance (draft)

This candidate is stacked on PRs #38–#44. It does not authorize production deployment. Migration `1788281400000` requires the Agent COD collection migration `1788280800000` and every earlier custody migration.

`agent_cod_collection` is the immutable record of cash liability created during verified Agent COD delivery. Admins need a separate record for real money later remitted to Kentexa. This change creates append-only `agent_cod_remittance` rows with collection, amount, method, external receipt/reference, admin actor and UUID operation key. It does not rewrite a collection, treat the remittance as a new customer checkout payment, or trigger a second seller release.

The active Admin role can list one Agent's collections and their remaining balances. Recording payment requires a positive two-decimal amount, a method, an actual receipt or transfer reference, and a UUID operation key. The service locks the collection and sums prior remittances. An identical retry returns the prior row; reuse of the key with different facts is refused. A PostgreSQL insert trigger also locks the collection and rejects any insert that would exceed its liability, including direct writes outside the service. Remittance rows cannot be updated, deleted or truncated. Downgrade refuses if any have been recorded. The admin Agent page exposes this per-collection form after an administrator has independently verified receipt of cash or transfer.

This is a recording and reconciliation action, not a payment provider integration. No automatic cash transfer, seller payout or offset against Agent earnings is inferred. There is no historical backfill. Review references, partial payment handling, admin role enforcement, and the existing Super Agent remittance route separately; that older route retains its prior balance model. Isolated PostgreSQL tests cover partial remittance, identical retry, mismatched retry, concurrent over-remittance, database trigger bypass and immutable rollback refusal.
